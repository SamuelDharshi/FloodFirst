# FEEDBACK: the missing cross-group nullifier guard in Semaphore, and what we built to close it

> **One-line summary.** Semaphore v4 stores spent nullifiers *per group*. Any programme with **several independent groups** (several NGOs, several DAOs, several schools) that wants "one person, one payment" across all of them gets **no protection from Semaphore itself**: the same person, enrolled by two groups, is accepted twice. We reproduced this with real zero-knowledge proofs, built a gas-cheap shared guard (`NullifierRegistry`), and propose a small, backwards-compatible primitive that would let every Semaphore integrator get this for free.

---

## 1. Scope and honesty (read this first)

- **What "sponsor technology" means here.** The hackathon page names the organisers (SMU SCIS, GSR Foundation, University of Málaga, DoraHacks) but does not mandate a tool. Our PRD's recommended stack is **Semaphore v4** (Privacy & Scaling Explorations) for private membership and nullifiers, an **EVM testnet** (Base Sepolia) and **GloFAS flood data** (via Open-Meteo). The strongest, provable finding is about Semaphore; secondary findings on the other pieces are in section 10.
- **This is a design gap, not a verifier bug.** The Semaphore code says so itself ("already used *inside the group*"). We do **not** claim the maintainers overlooked it, only that integrators who read "nullifiers prevent double use" can easily miss that the guarantee stops at the group boundary.
- **What we have not done.** We did not file an upstream issue/PR, did not test on mainnet, and measured gas on a local EVM. Findings refer to `@semaphore-protocol/contracts` **v4.14.5**.
- **Everything below is reproducible** with one command (section 4).

## 2. The problem in one picture

```
             SAME HOUSEHOLD  (one secret  ->  one identity)
                    |                         |
        enrolled by NGO A            enrolled by NGO B
        (Semaphore group 0)          (Semaphore group 1)
                    |                         |
        proof, scope = event 1       proof, scope = event 1
        nullifier = N                nullifier = N      <-- identical (same identity + same scope)
                    |                         |
     validateProof(group 0, proof)   validateProof(group 1, proof)
        spent[0][N] = true             spent[1][N] = true   <-- a DIFFERENT storage slot
                    |                         |
                ACCEPTED                  ACCEPTED         <-- household paid TWICE
```

The nullifier is computed **inside the circuit** from the identity and the *scope*, with no reference to the group. So the *evidence* of the double use (same `N`) is right there on chain, but the contract only looks for it in the slot of the group being used.

## 3. The real pain point

**Who is hurt:** every social-good programme that coordinates *several* organisations. Typical examples: aid agencies serving the same villages, school-meal programmes across districts, multi-clinic vaccination drives, multi-DAO grants.

**What goes wrong:** the very property that makes privacy-preserving registries attractive here, *"organisations can deduplicate without sharing beneficiary lists"*, is the property Semaphore does not enforce across groups. Teams discover it late (we discovered it while designing the PRD's central claim), then re-implement a global spent-set by hand, each with its own mistakes.

**Why it matters for the hackathon's mission** ("transparency, trust, inclusion"): a duplicate payment is not an abstract bug. It is aid taken from another household. A shared guard that is audited once and reused is cheaper and safer than every team inventing one.

What the first test does, step by step:
1. Fixture 0 = household 1 proving membership in **NGO A's** group for event 1; fixture 1 = the **same** household proving membership in **NGO B's** group for event 1.
2. `assertEq(a.nullifier, b.nullifier)` passes: same identity + same scope gives the same nullifier.

4. Replaying `a` in group A reverts with `Semaphore__YouAreUsingTheSameNullifierTwice`, which shows the protection *does* work inside one group (this is why the gap is easy to miss).

## 5. Root cause (with code)

`Semaphore.sol` (v4.14.5), lines 131-145:

```solidity
function validateProof(uint256 groupId, SemaphoreProof calldata proof) external override {
    // The function will revert if the nullifier that is part of the proof,
    // was already used inside the group with id groupId.
    if (groups[groupId].nullifiers[proof.nullifier]) {
        revert Semaphore__YouAreUsingTheSameNullifierTwice();
    }
    if (!verifyProof(groupId, proof)) revert Semaphore__InvalidProof();
    // Saves the nullifier so that it cannot be used again ... inside the group with id groupId.
    groups[groupId].nullifiers[proof.nullifier] = true;
    ...
```

and `ISemaphore.sol:20` declares the spent set **inside the group struct**: `mapping(uint256 => bool) nullifiers;`.

Two design facts combine:
1. The **nullifier does not depend on the group** (it depends on identity + scope).
2. The **spent set does depend on the group**.

Result: identical nullifiers in different groups never collide.

What the public documentation says (read on the [Semaphore FAQ](https://docs.semaphore.pse.dev/faq), checked while preparing this document):
- "The nullifier is the hash of the private key of the identity and the scope."
- The scope is "a topic on which users can generate a valid proof only once."
- In the voting example: if "you want all members of this group to vote only once, you can use the id of the group as the scope", and then store the nullifier and check whether it already exists.
- **The FAQ does not address one identity appearing in several groups.**

Following the group-id-as-scope advice makes cross-group detection impossible *by construction*, because the nullifiers then differ. An integrator who wants cross-group uniqueness must **choose an application-level scope** (we use the event id) *and* add their own global spent set. Nothing in the documentation we read tells them so.

## 6. What could have been done

| Option | Cross-group guarantee | Trust | Extra gas | Compatibility | Verdict |
| --- | --- | --- | --- | --- | --- |
| **A. Do nothing** (status quo) | none | n/a | 0 | n/a | every team re-invents it |
| **B. Off-chain dedup by a coordinator** | yes | trusted coordinator sees nullifiers | 0 on chain | easy | defeats the point of Web3 here |
| **C. Hard-code a global spent set in `Semaphore`** | yes | none | ~0 | **breaks** apps that rely on per-group reuse and *lets unrelated apps collide on a scope id* | too blunt |
| **D. Opt-in scoped primitive, namespaced by the calling contract** | yes, per application | none | ~0 | fully backwards compatible | **recommended** |
| **E. "Federated group" (a group of groups)** | yes | none | higher, new tree | new concept, migration | heavy |

## 7. Near-perfect solution

**Proposal: an opt-in, application-namespaced spent set.** Keep `validateProof` exactly as is. Add one function and one mapping:

```solidity
/// spent[caller][scope][nullifier] : namespaced by the verifying contract, so two applications can never collide
mapping(address => mapping(uint256 => mapping(uint256 => bool))) private spentScoped;

error Semaphore__NullifierAlreadySpentForScope();

/// Verifies membership of ANY group and spends the nullifier once per (caller, scope), across all groups.
function validateProofScoped(uint256 groupId, SemaphoreProof calldata proof) external {
    if (spentScoped[msg.sender][proof.scope][proof.nullifier]) revert Semaphore__NullifierAlreadySpentForScope();
    if (!verifyProof(groupId, proof)) revert Semaphore__InvalidProof();
    spentScoped[msg.sender][proof.scope][proof.nullifier] = true;
    emit ProofValidatedScoped(msg.sender, groupId, proof.scope, proof.nullifier, proof.message);
}
```

**Why this is close to perfect:**
- **Gas-neutral.** Measured: verification alone is **239,064** gas; `validateProof` (verify + store) is **266,472**, so storing the nullifier costs about **27,400** gas. A scoped store is the *same single `SSTORE`*, so the new primitive costs essentially nothing extra.
- **No new trust.** No coordinator; the spent set is public and deterministic.
- **No collisions between applications.** Namespacing by `msg.sender` means two programmes using the same scope integer cannot block each other.
- **Fully backwards compatible.** Existing groups and integrators are untouched.
- **Privacy preserved.** It stores only the nullifier that is already public in the proof.
- **Composable.** The caller still binds the claim to a recipient through `proof.message`, and decides who may call (our `NullifierRegistry` restricts callers to admitted groups).

**Security considerations we checked or would require before an upstream PR:**
1. **Front-running / redirection:** bind the payout to `proof.message` (we use a voucher id). A relayer cannot change it without invalidating the proof (tested: `test_tamperedMessageRejected`).
2. **Forged nullifier:** rejected by the proof (tested: `test_tamperedNullifierRejected`).
3. **Scope squatting:** namespacing by caller removes cross-application squatting.
4. **Admission control:** the *application* must decide which groups are valid (ours: `registerNgoGroup`, owner-gated, capped at 64 groups to bound loops).
5. **Residual limit (cannot be fixed in the protocol):** one person with **two different secrets** enrolled twice still looks like two people. This is a property of anonymous credentials, stated in our UI.

## 10. Other pain points we hit (measured, ranked by impact on the PRD's users)

1. **Proving artifacts are fetched at proof time.** `generateProof` downloads the circuit files from `snark-artifacts.pse.dev` unless you pass them in. Measured sizes (HTTP `Content-Length`): depth 1 = 1.55 MB zkey + 1.80 MB wasm = **3.35 MB**; depth 20 = **5.74 MB**; depth 32 = **7.71 MB**. For the PRD's *"household with a basic phone and no data connection"* this makes the first proof depend on connectivity. The API already accepts local artifacts, so the fix is documentation plus a recommended pattern: self-host and pre-cache them (service worker). **We have not implemented this yet.**
2. **Public RPC `eth_getLogs` is capped at 200 blocks** on `sepolia.base.org` (we hit `eth_getLogs is limited to a 200 range`). Base produces a block every ~2 s, so 200 blocks is under 7 minutes: indexing from a deploy block 28,000 blocks old needs about 140 requests. We worked around it (chunked, restartable indexer). A documented archive or indexed endpoint for hackathon teams would remove a day of work.
3. **GloFAS point lookup is silently ambiguous.** The Open-Meteo flood API returns the *largest river within a 5 km cell* and no river identity or upstream area. Near Guwahati, `26.20, 91.65` returned **1.67 m³/s** while `26.19, 91.70` returned **6,530 m³/s** (the Brahmaputra main stem). A parametric trigger pointed at the wrong cell would never fire, with no error. We now document the verified coordinates; returning the cell's upstream area would let integrators validate it.
4. **Default Merkle-root validity of one hour** (`merkleTreeDuration = 1 hours`, `Semaphore.sol:36,44`). Reasonable, but wallet-less or delayed relays should know that a root superseded by a later enrolment expires for in-flight proofs after an hour; this deserves a line in the integration guide.

## 11. Recommendations (short and actionable)

For **Semaphore maintainers:** add the opt-in scoped primitive (section 7) or publish a reference "multi-group guard"; add a docs page "Preventing duplicates across groups"; document artifact self-hosting for offline-first apps.
For **hackathon organisers:** publish a recommended RPC with a larger `eth_getLogs` window; list known cross-group pitfalls in the Social Good track brief.
For **data providers:** return river identity and upstream area with point queries.

## 12. Limitations of this document

- Evidence is from **v4.14.5** and a **local EVM**; gas on Base may differ slightly.
- We did not audit Semaphore or our registry. **Our contracts have had no independent audit.**
- The proposal in section 7 is a design sketch, not a tested upstream patch.
- We make no claim about who knew what; only about what the code does and what we reproduced.
